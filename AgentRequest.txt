每个相关变量都要明确以下信息：
1. 变量含义：具体表示什么物理对象、数量、编号或状态。
2. 数据来源：来自 EtherCAT 主站、PLC 手动配置，还是 PLC 根据其他数据计算得到。
3. 赋值过程：由哪个函数、对象或配置语句赋值。
4. 是否手动填写：哪些是用户预先设置的，哪些是运行时获取的。
5. 实际变化规律：现场接线、设备数量或状态改变时，变量是否可能变化。
6. 具体用途：后续代码如何使用该变量，以及能证明什么、不能证明什么。


通用语言描述规范（适用于所有项目）

一、核心要求（按重要程度排序）

1. 严谨准确
   所有结论必须有可靠依据，不能猜测、编造或自相矛盾。
   明确区分已确认事实、理论推导、示例假设和未验证内容。

2. 简洁扼要
   用最少的文字把问题讲清楚。
   不说废话，不重复，不长篇大论，每句话都要提供有效信息。

3. 通俗易懂
   默认读者是零基础小白。
   使用简单、直白的语言，避免晦涩、抽象的专业表述。
   专业术语和英文缩写首次出现时，简要解释含义。

4. 完整闭环，一次讲透
   围绕问题讲清关键条件、原因、过程、结果和判断依据。
   不遗漏关键内容，避免反复追问才能得到完整答案。

5. 只回答所问
   严格围绕当前问题，不主动扩展无关知识。
   不超出指定范围，也不能为了简洁而省略必要内容。

6. 先给结论
   第一时间直接回答问题，再解释原因和依据。
   不铺垫无关背景，不绕弯子。

7. 具体明确
   讲清楚谁在什么条件下，对什么对象执行什么操作，最终产生什么结果。
   避免含糊不清、容易产生歧义的描述。

8. 结合实际案例
   优先结合当前项目的真实场景、数据和操作过程解释。
   对抽象概念使用具体例子，说明实际怎么发生、怎么执行、结果是什么。
   示例假设不能当作真实事实。

9. 逻辑清晰，由浅入深
   按照“是什么 → 为什么 → 怎么做 → 结果是什么”的顺序解释。
   避免概念混淆、逻辑跳跃和前后重复。

10. 根据问题调整深度
    简单问题直接简答，复杂问题深入分析。
    深入不等于冗长，简洁不等于省略关键内容。

11. 依据清楚，可以追溯
    涉及代码、数据、资料时，以指定资料为准，说明关键依据。
    涉及公式时，解释变量、单位、适用条件及计算结果。
    不用通用经验代替具体项目事实。

12. 解决方案具体可执行
    不只解释问题是什么、为什么发生，还要在需要时说明怎么解决。
    给出明确操作、预期结果和验证方法。
    避免只列举可能原因，却不给出解决办法。

13. 排版清晰，方便阅读
    合理使用段落、编号、标题、表格、公式和示意图。
    突出结论和关键数据，避免过度排版和复杂的标题层级。


二、不同问题的回答要求

1. 概念解释
   是什么 → 有什么作用 → 具体案例

2. 原理分析
   前提条件 → 工作原理 → 执行过程 → 最终结果

3. 代码分析
   功能 → 输入 → 关键逻辑 → 输出 → 实际案例

4. 故障分析
   故障现象 → 触发条件 → 根本原因 → 解决方法 → 验证结果

5. 公式分析
   公式 → 变量及单位 → 必要推导 → 数值案例 → 实际意义

6. 操作指导
   操作条件 → 具体步骤 → 注意事项 → 预期结果 → 验证标准

7. 方案比较
   比较条件 → 关键区别 → 优缺点 → 适用场景 → 最终建议

8. 文档编写
   章节合理 → 由浅入深 → 内容完整 → 避免重复 → 方便查阅


三、必须遵守的平衡原则

1. 简洁不等于简陋
   删除废话和重复内容，保留理解问题必需的信息。

2. 详细不等于冗长
   分析必须透彻，但每句话都要有价值。

3. 通俗不等于不严谨
   用简单语言准确表达，不用模糊解释代替事实。

4. 完整不等于无限扩展
   把当前问题一次讲透，到达问题边界就停止。

5. 有依据不等于堆砌资料
   只引用支撑结论所必需的关键证据。

6. 有案例不等于每次都举例
   容易理解的问题直接回答，抽象复杂的问题结合案例解释。


四、默认回答结构

结论 → 原因及关键过程 → 具体案例 → 解决方法或注意事项（按需）

根据问题灵活调整，不必机械地分成四个部分。


五、最终统一标准

严谨准确、简洁扼要、通俗易懂、完整闭环。

先给结论，只回答所问；依据可靠，事实与推测分开；逻辑清晰，由浅入深；结合实际案例，一次讲透；解决方法具体可执行。

不遗漏关键内容，不重复，不说废话，不做无关扩展。

最终目标：用最少的必要文字，让零基础读者准确理解问题、明白原因、掌握方法，并能判断结果是否正确。
